# PRD 4: Open Source Mini Challenge (one meaningful pull request)

**Goal:** make a real contribution to an existing public repo during the hackathon window (since Aug 31, 2026), and submit it alongside the main project. No separate project needed.

## 1. What the rules say

- Allowed: a **new open-source repo with a license, a branch, a fork, or a pull request**. **PRs do not need to be merged**; a fork with your unmerged work is fine.
- Required submission fields: **contribution URL, project repo URL, GitHub username, and a description** of what you did, how it works and why it matters.
- Judges' examples: *obvious* = README update, typo fix, minor formatting. *Creative* = **meaningful feature with tests, a bug fix that unblocks other developers, a new integration pattern**.
- Only one mini challenge prize per project, but you can enter both mini challenges.

So aim for a **small but real code change with a test**, not a typo.

## 2. Plan

One quality PR, about 6 to 8 hours total over Days 1 to 8.

### Step 1: Choose a repo (Day 1)

A good target is:

- Python (you know it) and related to MCP or agents, so you learn what you are building
- Active (commits in the last month) with a CONTRIBUTING file
- Has issues labelled `good first issue` or `help wanted`

Places to look (verify each is active, and read its rules):

- The official MCP repos on GitHub (Python SDK, servers, Inspector)
- Kiro Crew's repo (`kirodotdev/KiroCrew`), which is new and open to contributors; this also strengthens your AWS story
- Search GitHub: `label:"good first issue" language:python mcp`

### Step 2: Pick ONE issue (Day 2)

- Choose something you can understand fully in an hour
- Comment on the issue: "I'd like to work on this. My plan is..." and wait for a quick yes if the repo asks for it
- Avoid issues already claimed

### Step 3: Fix + test (Days 3 to 4)

1. Fork, clone, create a branch
2. Run the repo's tests first (they should pass before you change anything)
3. Make the smallest change that solves the issue
4. Add or update a test that fails before and passes after

### Step 4: Open the PR (Day 5)

- Link the issue, explain what and why, show test results
- Follow the repo's PR template and code style

### Step 5: Respond (Days 5 to 8)

- Reply to review comments within 24 hrs
- If there is no reply by Day 8, keep the PR open and keep your branch as proof

## 3. Rules of conduct (important)

- **Understand every line you submit.** Many projects reject low-quality or AI-generated PRs. Check each repo's policy, and do not mass-produce PRs
- One careful PR beats five rushed ones
- Be polite and patient: maintainers are volunteers

## 4. Hacktoberfest

Your PR may also count toward Hacktoberfest, but the 2026 format moved away from counting pull requests. Read **hacktoberfest.com/questions** before relying on it.

## 5. Acceptance criteria

- PR is open on a public repo, with a test
- You can explain the change in 2 sentences
- Submission fields are ready (template below)
- Backup: if the PR is not merged, the fork/branch link still counts

## 6. Submission text template

- **Contribution URL:** (PR link)
- **Project repo URL:** (your Family Admin Agent repo)
- **GitHub username:** (yours)
- **What I did:** Fixed/added \_\_\_ in \_\_\_.
- **How it works:** \_\_\_ (2 to 3 sentences, mention the test)
- **Why it matters:** This helps people who \_\_\_ because \_\_\_. I hit this while building an MCP server for the hackathon.

## 7. Risks and fixes

| Risk | Fix |
| --- | --- |
| Issue too hard | Switch by Day 3 to an easier one; keep the scope tiny |
| Maintainer silent | Fork/branch counts; link it |
| Only typos available | Add a small test or example in the docs with working code instead |
| Time overrun | Cap this workstream at 1 hour a day |
